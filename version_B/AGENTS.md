# Setuk-AI 프로젝트 지침

이 저장소는 교사가 학생별 세부능력 및 특기사항을 작성하고 로컬 Linter로 검증하는 작업 하네스다. 일반적인 개발 요청에는 저장소의 기존 개발 규칙만 적용하고, 아래 세특 파이프라인은 개별 학생의 세특 작성을 명시적으로 요청했을 때만 실행한다.

## 세특 파이프라인 트리거

다음 의도가 분명한 요청에만 파이프라인을 실행한다.

- `<식별자> 세특 작업 시작해`
- `학생정보/<식별자>.yaml로 세특 작성해`
- `보고서/<파일명>.docx로 세특 작성해`
- 특정 학생 YAML을 지정한 동등한 세특 작성 요청

기획, 개발, 테스트, 규칙 수정, 예시 설명 요청에는 파이프라인을 실행하지 않는다. 식별자가 없거나 둘 이상으로 해석되면 작업을 시작하지 말고 하나의 입력 파일을 지정해 달라고 요청한다.

## 창체(진로활동·자율활동) 파이프라인 트리거

세특과는 별도의 파이프라인이다. 다음 의도가 분명한 요청에만 실행한다.

- `<식별자> 진로활동 작성해`
- `<식별자> 자율활동 작성해`
- `학생정보/<식별자>_진로.yaml로 창체 작성해` 또는 `학생정보/<식별자>_자율.yaml로 창체 작성해`
- 위와 동등한, 항목(진로활동 또는 자율활동)이 명확한 창체 작성 요청
- `<식별자> 창체 분류해줘` (분류 전용 D모드. 항목을 아직 정하지 않고 AI가 진로/자율 후보를 나눠 보고하는 요청이므로, 아래 "학생명과 항목 중 하나라도 불명확하면 확인 요청" 규칙에서 항목 미지정은 예외로 둔다.)

세특 트리거와 마찬가지로 기획·개발·테스트·규칙 수정 요청에는 실행하지 않는다. D모드를 제외한 창체 요청에서 학생명과 항목(진로활동/자율활동) 중 하나라도 불명확하면 작업을 시작하지 말고 확인을 요청한다.

## 공통교육 대체 창체 파이프라인 트리거 (땜빵모드)

창체(C모드)와는 별도의, 학생별 실제 활동이 없어 학교 전체가 공통으로 이수한 필수교육만으로 진로활동·자율활동을 작성해야 할 때 쓰는 파이프라인이다. 다음처럼 "땜빵모드"라는 시동어로 시작하고, 학생명·항목(진로활동 또는 자율활동)·우선순위가 매겨진 활동 목록이 함께 오는 요청에만 실행한다.

- `땜빵모드 <학생명> 학생 <진로활동|자율활동> 작성해줘, 활동 우선순위는 다음과 같아` 뒤에 우선순위별 활동명 목록
- 위와 동등한, "땜빵모드" 시동어와 학생명·항목·우선순위 활동 목록이 모두 명확한 요청

"땜빵모드" 시동어가 없으면 이 파이프라인을 실행하지 않는다 — 시동어 없이 학생명과 항목만 오는 요청은 그대로 C모드(보고서 기반) 트리거로 처리한다. 이 파이프라인은 실제 보고서(`.docx`)를 읽지 않고 사용자가 채팅에 직접 입력한 활동 목록만 근거로 사용한다.

## 물리학 통합 세특 파이프라인 트리거

일반 세특(A·B)이나 창체와는 별도의, 물리학 과목 전용 파이프라인이다. 다음처럼 자기성찰(선택)·물리신문·주제탐구 세 보고서를 하나의 세특으로 통합하려는 의도가 분명한 요청에만 실행한다.

- `<식별자> 물리 통합 세특 작성해`
- 위와 동등한, 자기성찰·물리신문·주제탐구를 하나로 합쳐 달라는 의도가 명확한 물리학 세특 요청

세특·창체 트리거와 마찬가지로 기획·개발·테스트·규칙 수정 요청에는 실행하지 않는다. 이 트리거가 없으면 물리학 세특 요청도 기본적으로 A·B모드(보고서 1개)로 처리한다 — 즉 "물리 세특 작성해"만으로는 E모드를 실행하지 않는다.

## UTF-8 파일 입출력

한글 파일을 처음부터 정확히 읽는다. PowerShell에서 텍스트를 읽기 전에 다음 인코딩을 설정하고, 모든 `Get-Content` 호출에 `-Encoding UTF8`을 명시한다.

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new()
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
Get-Content -Raw -Encoding UTF8 -LiteralPath '<파일경로>'
```

- 기본 인코딩으로 먼저 읽은 뒤 깨지면 재시도하는 방식을 사용하지 않는다.
- YAML과 Markdown은 UTF-8로 저장한다. 가능하면 BOM 없이 저장한다.
- `Get-Item.Length`는 디스크 파일 크기일 뿐 NEIS 바이트 수가 아니다. Linter 실행 전에는 이를 NEIS 기준 바이트로 보고하지 않는다.

## 보호해야 하는 경계

- 한 작업에서는 지정된 학생 보고서 하나와 학생 YAML 하나만 읽는다. 단, 창체 파이프라인은 예외로 동일 학생·동일 항목(진로활동 또는 자율활동)의 보고서 여러 개를 한 작업에서 함께 읽을 수 있다. 이 예외는 창체 파이프라인과 물리학 통합 세특 모드(E)에만 적용되며, 그 외 세특 파이프라인(A·B)에는 적용하지 않는다.
- 창체 분류 전용 모드(D)는 위 예외를 더 넓힌다. 목적상 동일 학생의 진로+자율 후보 보고서 전체를 항목 구분 없이 한 작업에서 함께 읽을 수 있다. 단 이 경우 그 결과로 어떤 YAML·MD 파일도 생성하지 않아야 하며, 채팅 분류 보고로만 끝나야 이 확장 예외가 적용된다.
- 땜빵모드(F)는 `보고서/`를 전혀 읽지 않는다. 사용자가 채팅에 직접 입력한 활동 목록만 근거로 사용하며, 학생명이 포함된 `.docx`를 탐색하거나 열지 않는다.
- `학생정보/template.yaml`과 `학생정보/example.yaml`은 실제 학생 작업의 입력으로 사용하지 않는다.
- 다른 학생 보고서나 YAML의 내용을 검색하여 식별자를 추정하지 않는다.
- 보고서 원본은 항상 읽기 전용이다. 보고서 입력 단계에서 생성한 YAML은 저장 후 읽기 전용으로 취급한다.
- 중간 계약은 현재 채팅 컨텍스트에서만 전달하고 파일로 저장하지 않는다. 유일한 예외는 A·B·C·E모드의 초안 검토 체크포인트(`run_state/<식별자>.json`)이며, 이 파일은 "2-A. Human-in-the-Loop 체크포인트"가 정한 절차로만 만들고 지운다.
- 최종 본문 외의 학생정보를 `세특/` 또는 다른 파일에 복제하지 않는다.
- 학생 이름, 교사 이름, 학년, 반, 번호를 최종 본문에 넣지 않는다.
- 새 학생을 작업할 때는 새 채팅을 사용하도록 안내한다.
- 이 저장소는 `version_A/`(A버전, 웹 업로드용, git 태그 `v1.0.2-a-frozen` 시점에 동결), `version_B/`(이 폴더, B버전), `version_C/`(C버전, Claude API 직접 호출) 세 버전으로 나뉘어 있다. 이 문서가 다루는 세특·창체 파이프라인은 `version_B/` 안에서만 동작하며, `version_A/`나 `version_C/`의 내용을 읽거나 수정하지 않는다. 다른 버전의 유지보수가 명시적으로 요청된 경우에만 예외로 다룬다.

## 1. 진입 모드와 입력 파일 결정

세특 요청이면 A·B 중 하나만, 창체 작성 요청이면 C만, 창체 분류 요청이면 D만, 물리학 통합 세특 요청이면 E만, "땜빵모드" 시동어가 있는 공통교육 대체 창체 요청이면 F만 선택한다.

### A. 보고서 입력 모드 (세특)

- 학생명만 지정하거나 `보고서/<파일명>.docx`를 지정한 요청의 기본 모드다.
- `.agent/01_report_ingestion.md`를 읽고 보고서 하나를 `학생정보/<학생명>.yaml`로 변환한다.
- 결과가 `REPORT_NEEDS_INPUT_V1`이면 즉시 중단하고 질문만 사용자에게 전달한다.
- 결과가 `REPORT_INGESTED_V1`이면 계약의 `yaml_path`만 다음 단계 입력으로 사용한다.
- 동일한 YAML이 이미 있으면 01단계 지침에 따라 덮어쓰기 승인을 받는다. 승인 전에는 기존 YAML을 읽거나 변경하지 않는다.
- 보고서 후보가 없으면 현재 열려 있는 작업공간의 `보고서/` 절대 경로와 그 안의 DOCX 파일명만 확인한다. 새 버전 ZIP을 풀어 실행 중이라면 기존 개발 폴더의 보고서가 자동 복사되지 않음을 설명한다.

### B. 기존 YAML 직접 입력 모드 (세특)

- 사용자가 `학생정보/<식별자>.yaml` 경로를 명시한 경우에만 사용한다.
- 해당 YAML이 정확히 존재해야 하며 `.agent/01_report_ingestion.md`를 생략한다.
- 경로를 정규화했을 때 `학생정보/` 밖을 가리키거나 확장자가 `.yaml`이 아니면 거부한다.
- 다른 YAML의 내부를 검색하여 파일을 찾지 않는다.

A·B 모드에서 입력 YAML이 결정되면 출력 경로는 YAML stem을 그대로 사용한 `세특/<식별자>.md`로 고정한다. 출력 파일이 이미 있으면 쓰기 전에 덮어써도 되는지 명시적으로 확인한다. 사용자가 현재 요청에서 재작성 또는 덮어쓰기를 이미 허용했다면 다시 묻지 않는다.

### C. 순위 기반 다중 보고서 입력 모드 (창체 전용)

- 사용자가 학생명, 항목(진로활동 또는 자율활동)과 함께 활동별 순위 목록(예: "학문 융합 프로젝트 1순위, 종합 탐구 보고서 2순위, 세기의 학자 탐구 3순위")을 제공한 경우 사용한다.
- `보고서/`에서 파일명에 해당 학생명이 포함된 `.docx`를 모두 나열한다. 문서 내용을 열어 학생을 탐색하지 않는다.
- 순위 목록의 각 항목 키워드가 파일명에 포함된 파일을 하나씩 매칭한다. 찾은 `.docx`가 5개이고 순위 목록이 3개 항목이면, 매칭되지 않은 나머지 2개는 사용하지 않는다.
- 각 순위 항목에 매칭되는 파일이 정확히 하나면 추가 확인 없이 바로 사용한다. 항목에 매칭되는 파일이 없거나 둘 이상이면 그 항목만 사용자에게 확인한다.
- 순위 목록 없이 학생명과 항목만 지정된 경우에는 파일명에 학생명이 포함된 `.docx`를 모두 후보로 제시하고, 사용할 파일과 순서를 사용자에게 확인받은 뒤 진행한다.
- 최종 결과물의 활동 배치 순서는 사용자가 지정한 순위(1→2→3)를 그대로 따른다.
- 입력 YAML은 `학생정보/<식별자>_<항목>.yaml`(항목은 `진로` 또는 `자율`)로 고정하며, 이미 있으면 A·B 모드와 동일하게 덮어쓰기 승인을 받는다.
- 출력 경로는 `창체/<식별자>_<항목>.md`로 고정한다. 출력 파일이 이미 있으면 쓰기 전에 덮어써도 되는지 명시적으로 확인한다.
- **적용 규칙 파일:** 진로활동·자율활동 모두 `rules.json`(최대 1,500바이트)을 그대로 사용한다. (2026년 기준 진로활동도 1,500바이트로 확인됨. 이후 기재요령이 바뀌면 이 값을 다시 조정한다.)

### D. 분류 전용 모드 (창체)

- `<식별자> 창체 분류해줘` 요청에만 사용한다. 순위 목록이나 항목(진로활동/자율활동) 지정을 사용자가 미리 하지 않는다 — 이 모드의 목적이 그 분류 자체를 대신 해 주는 것이다.
- `.agent/01d_activity_classification.md` 하나만 실행하고 종료한다. A·B·C 모드처럼 02·03c·04 단계로 이어지지 않으며, YAML이나 `창체/*.md` 파일을 만들지 않는다.
- 아래 "2. 지침을 순서대로 실행"부터 "6. 완료 보고"까지의 단계·Linter·승인 게이트는 D모드에 적용하지 않는다. `01d`가 정의한 채팅 보고 형식으로 끝난다.

### E. 물리학 통합 다중 보고서 입력 모드 (세특 전용)

- "물리학 통합 세특 파이프라인 트리거" 요청에만 사용한다. 자기성찰(선택)·물리신문·주제탐구 세 보고서를 한 세특으로 통합한다.
- `보고서/`에서 파일명에 해당 학생명이 포함된 `.docx`를 모두 나열한다. 문서 내용을 열어 학생을 탐색하지 않는다. `~$`로 시작하는 Word 임시 파일은 제외한다.
- 역할은 다음 순서로 배타적으로 매칭한다(한 파일은 한 역할에만 속한다). 먼저 매칭된 역할이 해당 파일을 가져가고, 뒤 순서 역할은 이미 가져간 파일을 다시 매칭하지 않는다.
  1. 자기성찰(선택): 파일명에 "자기성찰" 또는 "자기평가"(띄어쓰기 변형 포함)가 포함된 파일.
  2. 물리신문: 남은 파일 중 파일명에 "신문"이 포함된 파일.
  3. 주제탐구: 남은 파일 중 파일명에 "탐구"가 포함된 파일.
- 물리신문·주제탐구는 각 역할에 매칭되는 파일이 정확히 하나여야 바로 사용한다. 매칭이 없거나 둘 이상이면 그 역할만 사용자에게 확인한다.
- 자기성찰은 매칭이 없으면(0개) 조용히 생략하고 태도 문단 없이 진행한다. 단, 위 세 역할 중 어디에도 매칭되지 않은 학생명 포함 파일이 남아 있으면 조용히 무시하지 않고 "이 파일이 자기성찰 보고서인지" 사용자에게 확인한다. 자기성찰에 매칭이 둘 이상이면 다른 역할과 동일하게 확인을 요청한다.
- 물리신문·주제탐구 둘 다 0매칭이면(자기성찰 존재 여부와 무관) YAML을 만들지 않고 작업을 중단한 뒤, 이 학생은 통합 모드 대상 자료가 부족하다고 교사에게 별도로 보고한다. 다른 모드로 임의 전환하지 않는다.
- `.agent/01e_physics_report_ingestion.md`를 읽고 확정된 보고서를 `학생정보/<식별자>_물리세특.yaml`로 변환한다. 결과가 `REPORT_NEEDS_INPUT_V1`이면 즉시 중단하고 질문만 사용자에게 전달한다.
- 동일한 YAML이 이미 있으면 A·B 모드와 동일하게 덮어쓰기 승인을 받는다.
- 출력 경로는 YAML stem을 따르지 않고 `세특/<식별자>.md`로 고정한다(A·B 모드의 "YAML stem 그대로 사용" 규칙의 예외). 출력 파일이 이미 있으면 쓰기 전에 덮어써도 되는지 명시적으로 확인한다.

### F. 공통교육 대체 입력 모드 (땜빵모드, 창체 전용)

- "공통교육 대체 창체 파이프라인 트리거 (땜빵모드)" 요청에만 사용한다. 보고서(`.docx`)를 전혀 읽지 않고, 사용자가 채팅에 직접 입력한 활동 목록만으로 진로활동 또는 자율활동 특기사항을 작성한다.
- `.agent/01f_common_education_drafting.md` 하나만 실행한다. C모드와 달리 `02_data_structuring.md`·`03c_activity_drafting.md`·`04_evaluation.md`는 사용하지 않는다 — 개별 학생 근거 문서가 없어 그 단계들의 전제(추출된 명제, 개인별 역량 근거)가 성립하지 않기 때문이다.
- 활동명은 `01f_common_education_drafting.md`의 "공통교육 목록" 6개 항목에만 대응해야 한다. 목록에 없는 활동명이 오면 임의로 항목을 만들지 않고 사용자에게 확인한다.
- 입력 YAML은 `학생정보/<식별자>_<항목>.yaml`로 고정하며, 이미 있으면 C모드와 동일하게 덮어쓰기 승인을 받는다.
- 출력 경로는 `창체/<식별자>_<항목>.md`로 고정한다. 출력 파일이 이미 있으면 쓰기 전에 덮어써도 되는지 명시적으로 확인한다.
- **적용 규칙 파일:** `rules.json`의 `max_bytes`(1,500바이트)만 상한으로 적용한다. `target_min_bytes`(권장 하한)는 이 모드에 적용하지 않는다 — 사용자가 분량을 채울 필요가 없다고 확정했다.

## 2. 지침을 순서대로 실행

아래 문서는 한꺼번에 모두 읽지 말고 해당 단계가 시작될 때 하나씩 읽는다. 각 문서의 입력·출력 계약과 중단 조건을 그대로 따른다.

### 세특 모드 (A·B)

1. 보고서 입력 모드라면 `.agent/01_report_ingestion.md`를 먼저 완료한다. 기존 YAML 직접 입력 모드에서만 이 단계를 생략한다.

4. `.agent/03_drafting.md`를 읽고 `STRUCTURED_FACTS_V1`에서 `DRAFT_V1`을 생성한다.
5. `.agent/04_evaluation.md`를 읽고 두 계약을 검토한 후 계약의 `output_path`에 최종 본문을 저장한다.

4번과 5번 사이에는 "2-A. Human-in-the-Loop 체크포인트"를 반드시 거친다.

5. `.agent/04_evaluation.md`를 읽고 두 계약을 검토한 후 계약의 `output_path`에 최종 본문을 저장한다. (세특 모드와 동일한 지침을 그대로 사용한다.)

단계를 생략하거나 순서를 바꾸지 않는다(F모드는 원래 단일 단계이므로 해당 없음). 후속 단계는 앞 단계와 입력 YAML에 없는 사실을 추가할 수 없다. `source_path` 또는 `output_path`가 단계 사이에서 달라지면 학생정보 혼선으로 간주하여 저장하지 않고 중단한다.

## 2-A. Human-in-the-Loop 체크포인트 (초안 검토, run_state)

세특 모드(A·B), 창체 모드(C), 물리 통합 모드(E)에서는 03(또는 03c/03e)이 만든 `DRAFT_V1`을 04로 곧바로 넘기지 않는다. 교사가 초안을 직접 검토·승인한 뒤에만 04를 실행한다. D모드와 F모드는 이 체크포인트를 사용하지 않는다 — D는 어떤 YAML·MD 파일도 만들지 않고, F는 02·03·04 자체를 거치지 않기 때문이다.

이 체크포인트는 `run_state/<식별자>.json`(스키마와 상태값은 `기획서.md` 6.3)에 기록하며, `scripts/run_state.py`와 `scripts/review_cli.py`로만 읽고 쓴다. 두 스크립트는 문장을 생성하지 않는 결정적 도구이며, 3번(Linter 실행 파일 결정)과 동일하게 반드시 `python_portable/python.exe`로 실행하고 시스템 Python을 쓰지 않는다.

1. 파이프라인 시작 직후 체크포인트를 만든다.
   ```powershell
   & '.\python_portable\python.exe' '.\scripts\run_state.py' 'init' '<식별자>' '<모드문자>'
   ```
   `<모드문자>`는 현재 실행 중인 모드 하나(`A`, `B`, `C`, `E`)를 그대로 쓴다.
2. 01단계(보고서 입력 또는 YAML 직접 지정) 완료 후 `set-report-ingested --yaml-path <경로>`를, 02단계 완료 후 `set-structured`를 실행해 진행 상태를 기록한다.
3. 03(또는 03c/03e)이 `DRAFT_V1.text`를 완성하면 그 본문을 임시 파일로 저장한 뒤 다음을 순서대로 실행한다.
   ```powershell
   & '.\python_portable\python.exe' '.\scripts\run_state.py' 'set-drafted' '<식별자>' '--draft-file' '<임시파일 경로>'
   & '.\python_portable\python.exe' '.\scripts\run_state.py' 'set-awaiting-review' '<식별자>'
   ```
4. `set-awaiting-review` 실행 후에는 04를 이어서 실행하지 않는다. 대신 사용자에게 다음을 안내하고 응답을 기다린다.
   - 검토 화면을 여는 정확한 명령: `& '.\python_portable\python.exe' '.\scripts\review_cli.py' 'open' '<식별자>'`
   - 승인 명령(`review_cli.py approve <식별자>`)과 반려 명령(`review_cli.py reject <식별자> --reason '<이유>'`)
   - 검토를 마치면 채팅으로 계속 진행해 달라고 알려 달라는 안내
5. 사용자가 검토를 마쳤다고 알리면 04를 실행하기 전에 반드시 현재 상태를 확인한다.
   ```powershell
   & '.\python_portable\python.exe' '.\scripts\run_state.py' 'show' '<식별자>'
   ```
   - `status`가 `REVIEWED`이면 `steps.review.edited_text`를 `DRAFT_V1.text` 대신 04의 입력 본문으로 사용해 04를 진행한다.
   - `status`가 `REVIEW_REJECTED`이면 04를 실행하지 않는다. `steps.review.reviewer_note`의 사유를 반영해 03(또는 03c/03e)부터 초안을 다시 작성한 뒤, 3번부터 이 체크포인트를 다시 거친다.
   - `status`가 여전히 `AWAITING_REVIEW`이면 검토가 끝나지 않은 것이므로 04를 실행하지 않고 아직 승인 대기 중이라고 보고한다.
   - 그 외 상태이면 진행 순서가 어긋난 것이므로 저장하지 않고 현재 상태를 그대로 보고한다.
6. 04가 최종 파일을 저장하면 Linter 실행 승인을 요청하기 전에 다음을 실행한다.
   ```powershell
   & '.\python_portable\python.exe' '.\scripts\run_state.py' 'set-evaluated' '<식별자>' '--output-path' '<저장한 파일 경로>'
   ```
7. `run_state.py`나 `review_cli.py`가 `[FATAL]` 오류를 반환하면 그 메시지를 그대로 사용자에게 전달한다. 오류 메시지를 자체 해석해 run_state 파일을 직접 고치지 않는다.

## 3. Linter 실행 파일 결정

최종 파일 저장 후 `python_portable/python.exe`를 사용한다. 파일이 없으면 시스템 Python으로 대체하지 말고 포터블 Python이 누락되었다고 사용자에게 보고한다.

시스템 PATH의 `python`, `python3`, `py`는 사용하지 않는다. 학생 파일과 규칙 파일 경로는 항상 별도 인자로 안전하게 전달하며 문자열로 조합한 동적 셸 명령을 만들지 않는다.

명령 형식은 다음과 같다. `<파일경로>`는 세특 모드(A·B)와 물리 통합 모드(E) 모두 `.\세특\<식별자>.md`, 창체 모드(C)와 땜빵모드(F) 모두 `.\창체\<식별자>_<항목>.md`를 그대로 사용한다.

```powershell
& '.\python_portable\python.exe' '.\linter.py' '<파일경로>' '--json'
```

세특·자율활동·진로활동 모두 규칙 파일을 생략해 기본 `rules.json`(1,500바이트)을 사용한다.

## 4. 실행 승인 게이트

Linter 명령을 바로 실행하지 않는다. 사용자에게 다음 내용을 보여 주고 명시적인 실행 동의를 기다린다.

- 검사할 최종 파일 경로
- 실행할 정확한 명령
- `Linter를 실행해도 될까요?`라는 승인 질문

창체 모드(C)에서는 위 항목 앞에 순위별 표를 먼저 제시한다. 표의 열은 `순위 | 사용 파일명 | 생기부에 반영된 문단`으로 하며, 최종 저장된 본문을 활동 경계(마침표 뒤 띄어쓰기)로 나누어 각 순위에 해당하는 문장 묶음을 그대로 인용한다. 문단 구분은 `.agent/01c_activity_report_ingestion.md`에서 기록한 `priority`·`source_report`를 근거로 한다. 이 표는 사용자가 Linter 실행을 승인하기 전에 출처를 검토할 수 있도록 승인 요청 메시지 안에 포함하며, 완료 보고(6번)에서는 다시 출력하지 않는다.

물리 통합 모드(E)에서도 동일하게 표를 먼저 제시한다. 표의 열은 `역할 | 사용 파일명 | 생기부에 반영된 문단`으로 하며, 문단 구분은 `.agent/01e_physics_report_ingestion.md`에서 기록한 `role`·`source_report`를 근거로 한다. 물리신문·주제탐구 중 하나가 품질 미달 또는 0매칭으로 제외되었다면 표 아래에 어떤 역할이 왜 빠졌는지 한 줄로 명시한다. 이 표도 승인 요청 메시지 안에 포함하며 완료 보고에서는 다시 출력하지 않는다.

땜빵모드(F)에서도 동일하게 표를 먼저 제시한다. 표의 열은 `우선순위 | 항목명 | 생기부에 반영된 문장`으로 하며, 문장 구분은 최종 저장된 본문을 마침표 뒤 띄어쓰기로 나눈 것을 우선순위 순서대로 근거로 한다. 이 표도 승인 요청 메시지 안에 포함하며 완료 보고에서는 다시 출력하지 않는다.

자기성찰의 "수업외 질문 횟수"가 5회 이상이어서 `.agent/03e_physics_drafting.md`의 기준대로 태도 문단에 적극 반영했다면, 위 표와는 별도로 태도 문단에 실제로 사용한 문장을 그대로 다시 보여주고 "이 표현이 적절한지 확인해 주시겠어요?"라고 별도로 확인을 받는다. 이 확인은 Linter 실행 승인 질문과는 별개이며, 확인을 받기 전에는 Linter 실행 승인 질문으로 넘어가지 않는다. 사용자가 표현 수정을 요청하면 그 수정을 반영한 뒤에만 다음 단계로 진행한다.

사용자가 승인하기 전에는 터미널 명령을 실행하지 않는다. IDE 자체의 도구 승인 설정과 관계없이 이 대화형 확인을 생략하지 않는다. 사용자가 거절하면 최종 파일은 그대로 두고 검증되지 않았다고 보고한 후 종료한다.

## 5. Linter 결과 처리와 자율 수정

Linter의 JSON 출력과 종료 코드를 함께 확인한다.

- 종료 코드 `0`: 오류 0건이다. 완료 절차로 이동한다.
- 종료 코드 `1`: `diagnostics`의 오류만 근거로 최종 본문을 최소 수정한다.
- 종료 코드 `2`: 입력 또는 설정의 치명적 오류다. 본문을 수정하지 말고 오류를 사용자에게 보고한다.
- JSON을 읽을 수 없거나 필수 필드가 없으면 본문을 수정하지 말고 실행 오류로 보고한다.

`BELOW_TARGET_LENGTH` 경고가 있으면 오류가 0건이어도 바로 완료하지 않는다. `STRUCTURED_FACTS_V1`의 미사용 근거를 검토해 사실·평가의 중복 없이 보강할 수 있으면 본문을 수정하고, 변경 이유와 명령을 제시한 뒤 재실행 승인을 받는다. 근거를 모두 사용해 더 늘릴 수 없으면 임의로 내용을 만들지 않고 평가 계약의 `length_exception_reason`과 함께 완료 보고한다. **땜빵모드(F)는 예외다** — `target_min_bytes`를 적용하지 않으므로 `BELOW_TARGET_LENGTH` 경고가 있어도 오류 0건이면 보강 시도 없이 바로 완료 절차로 이동한다.

종료 코드 `1`이면 다음 원칙으로 수정한다.

1. `BYTE_LIMIT`: 중복과 덜 중요한 표현부터 줄이며 핵심 행동·근거·성장은 보존한다.
2. `FORBIDDEN_TERM`: 진단된 표현을 삭제하거나 같은 사실을 허용되는 일반 표현으로 바꾼다. 사실 의미를 새로 만들지 않는다.
3. `UNSUPPORTED_CHARACTER`: 해당 문자만 제거하거나 허용된 일반 문자로 바꾼다.
4. `TAB_CHARACTER`: 탭을 일반 공백으로 바꾼다.
5. `EMPTY_CONTENT`: 자동으로 내용을 만들지 말고 입력 근거 부족으로 중단한다.
6. 알 수 없는 진단 코드는 임의로 고치지 말고 보고한다.

수정 후에는 변경 이유와 다시 실행할 정확한 명령을 보여 주고 `Linter를 다시 실행해도 될까요?`라고 별도 승인을 요청한다. 승인 없이 재검사하지 않는다. 오류가 0건이 될 때까지 같은 절차를 반복하되 다음 안전 중단 조건을 적용한다.

- 같은 진단 코드와 위치가 두 번 연속 반복됨
- 수정 후 바이트 수 또는 오류 수가 줄지 않음
- 재검사를 5회 수행했음
- 수정하려면 `STRUCTURED_FACTS_V1`에 없는 사실을 추가해야 함

안전 중단 시 현재 파일과 남은 오류를 보고하고 교사의 판단을 요청한다.

A·B·C·E모드는 Linter를 실행할 때마다(통과·실패 모두, 재검사 포함) 결과를 run_state에 기록한다. `<재시도횟수>`는 이번이 몇 번째 실행인지이며 최초 실행은 `0`이다.

```powershell
& '.\python_portable\python.exe' '.\scripts\run_state.py' 'set-linted' '<식별자>' '--result' 'pass' '--retry-count' '<재시도횟수>'
```

오류가 있으면 `--result fail`로 기록한 뒤 수정하고 재검사한다.

## 6. 완료 보고

오류가 0건이면 다음만 간결하게 보고한다.

- 저장된 최종 파일 경로
- 최종 바이트 수와 최대 바이트 수
- 목표 하한과 그 충족 여부. 미달이면 `length_exception_reason`
- Linter 오류 0건
- 교사가 본문을 검토한 뒤 NEIS에 복사해야 한다는 안내
- 다음 학생은 개인정보 혼선을 막기 위해 새 채팅에서 시작하라는 안내

A·B·C·E모드는 완료 보고 전에 `run_state/<식별자>.json`을 삭제해 체크포인트를 정리한다(`run_state/<식별자>_review.md`가 남아 있다면 함께 삭제한다). 삭제했다는 사실을 완료 보고에 한 줄로 포함한다.

창체 모드(C)의 순위별 표, 물리 통합 모드(E)의 역할별 표, 땜빵모드(F)의 우선순위별 표는 4번(실행 승인 게이트)에서 이미 제시했으므로 완료 보고에서는 다시 출력하지 않는다.

땜빵모드(F)는 "목표 하한과 그 충족 여부" 대신 "이 모드는 분량 하한을 적용하지 않음"을 한 줄로 보고한다.

물리 통합 모드(E)에서 자기성찰의 "수업외 질문 횟수"가 3~4회 구간이라 `.agent/03e_physics_drafting.md`의 재량 기준으로 태도 문단 포함 여부를 판단했다면, 그 판단(포함/미포함)과 이유를 완료 보고에 한 줄 추가한다.

물리 통합 모드(E)에서 자기성찰 활동을 `.agent/01e_physics_report_ingestion.md`·`.agent/03e_physics_drafting.md`의 예외 규칙에 따라 태도 문단이 아니라 실질적 탐구 활동으로 승격해 작성했다면, 그 판단 근거를 완료 보고에 한 줄 추가한다.

Linter 통과는 내용의 사실성이나 최신 학교생활기록부 지침 준수를 법적으로 보증하지 않는다. 최종 확인 책임은 교사에게 있음을 명시한다.
