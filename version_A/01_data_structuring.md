# 01. 전처리 모듈 (Data Structuring Module)

## 파이프라인에서의 위치

```
[docx 업로드, 활동 1건 이상] -> 전처리(본 모듈) -> 작성(02, INITIAL 모드) -> ...
```

교사가 학생의 활동 보고서 .docx 파일을 대화창에 업로드하면, 이 모듈이 원문을
읽고 02 이후 모든 모듈이 쓸 수 있는 구조화된 데이터로 정리한다.

**전제 1 (유지): 문서 한 개 안에서 여러 필드를 분리하지 않는다.** docx 파일
하나는 항상 하나의 필드(세특 한 과목, 또는 창체 한 종류)에 속하는 활동만
담고 있다고 가정한다. 한 파일 안에 자율활동과 세특이 섞여 있는 것처럼 보이면
임의로 분리하지 않고 `unresolved_conflicts`에 남긴다.

**전제 2 (변경됨): 여러 개의 docx를 하나의 세특으로 묶을 수 있다.** 같은
과목(세특) 또는 같은 항목(창체)에 대해 학생이 여러 건의 활동 보고서를
제출한 경우, 그 보고서들을 순서를 지정해 함께 업로드하면 하나의 최종
결과물로 묶어서 작성한다. 예: 물리학Ⅱ 주제탐구 보고서 2건을 순위와 함께
올리면 물리학Ⅱ 세특 하나에 두 활동이 순서대로 반영된다. 자세한 처리는
아래 "다중 보고서 모드" 절 참고. **문서를 하나로 합친다고 해서 활동 내용까지
하나의 서사로 뭉개는 것은 아니다** — 02(작성 모듈)가 각 활동을 독립된
문장 묶음으로 순서대로 이어붙이며, 절대 하나의 이야기로 합성하지 않는다.

**이 모듈을 거치지 않은 원문 텍스트가 02 이후 단계로 직접 전달되어서는 안 된다**
— 특히 개인정보 제거는 반드시 여기서 끝나야 한다.

## 입력

- 업로드된 .docx 파일의 텍스트 (Claude Project 환경이 업로드 시 자동으로 추출한
  텍스트를 그대로 읽는다. 별도 변환 스크립트를 실행하지 않는다.)

**주의: 업로드된 파일명은 절대 참고하지 않는다.** 파일명 자체에 학생 이름·학번이
포함되어 있는 경우가 흔하다(예: `30701_권미나_외_0명_물리학_II_주제탐구보고서.docx`).
`subject_label`이나 `student_context`를 채울 때 파일명이 아니라 반드시 **문서
본문 내 제목**을 사용한다.

## 템플릿 인식

문서의 표/제목 구조를 보고 어떤 보고서 양식인지 먼저 판별한다. 판별이 안 되면
임의로 field_type을 추정하지 말고 `unresolved_conflicts`에 남겨 교사에게 확인받는다.

| 인식 단서 | field_type | subject_label 추출 방법 |
|---|---|---|
| 제목에 "물리학 II", "화학 I" 등 특정 과목명 + "주제 탐구 보고서"/"심화 탐구 보고서" | `subject_setuk` | 제목에서 과목명만 추출 (예: "물리학 II 심화 주제 탐구 보고서" → "물리학II") |
| (향후 추가 예정) 자율활동 관련 양식 | `autonomous_activity` | 템플릿 확보 후 규칙 추가 |
| (향후 추가 예정) 동아리활동 관련 양식 | `club_activity` | 템플릿 확보 후 규칙 추가 |
| (향후 추가 예정) 진로활동 관련 양식 | `career_activity` | 템플릿 확보 후 규칙 추가 |

### 확정 템플릿 A: 교과 주제 탐구 보고서 (물리학 II 사례로 확정)

이 템플릿은 아래 섹션 구조를 갖는다. 섹션 제목이 정확히 일치하지 않아도
(예: "탐구동기"가 "연구 동기"로 되어 있어도) 의미상 대응되면 같은 역할로 처리한다.

| 문서 섹션 | 매핑 대상 |
|---|---|
| 제목 | 활동 주제 (raw_observations의 첫 항목으로) |
| Q1. 탐구동기 | `causal_chain.motivation` — 이 템플릿은 동기가 항상 명시적으로 분리되어 있으므로, 다른 입력과 달리 여기서는 원칙적으로 null을 쓰지 않는다 |
| 기본적인 배경지식 | 보조 맥락. 학생이 어떤 개념을 스스로 정리했는지 보여주는 사실이면 raw_observations에 짧게 포함, 교과서적 설명 그대로 길게 옮기지 않는다 |
| Q2. 탐구한 구체적인 내용 (본론) | `causal_chain.activity`의 핵심 원천. 실험 설계, 방법, 결과, 오차 분석 등 구체적 수치/과정을 raw_observations로 분해 (아래 "표 붕괴 처리" 참고) |
| 교과 내용과 조사한 내용의 연계성 | activity 또는 competency를 뒷받침하는 보조 사실 |
| 결론 요약 | `causal_chain.competency`의 핵심 원천 — 무엇을 확인/도출했는지 |
| Q3. 배운 것/새롭게 알게 된 것 | `causal_chain.competency` 보강 — 개념 이해, 오개념 수정 등 |
| Q4. 어려움과 해결 노력 | `causal_chain.competency` 보강 — 문제해결 과정. 활동의 서사적 연결(왜 2차 실험을 했는지 등)에도 쓰인다 |
| Q5. 타 분야와의 연계성 | 내용이 "없음"이면 무시. 실제 연계 내용이 있으면 raw_observations에 짧게 포함 |
| 향후 추가 탐구 계획 | 학생이 실제로 쓴 문장이면 사실이므로 포함 가능하나, 성취된 결과가 아니라 **의도/계획**임을 구분해서 다룬다는 점을 raw_observations 항목 자체에 남긴다 (예: "~하고자 하는 계획을 밝힘"으로, 이미 이룬 것처럼 쓰지 않는다) |
| 출처 | 부가 정보. 참고자료 활용 사실 정도로만 짧게, 필수는 아님 |

### 표 붕괴 처리 (실제 사례)

docx의 표가 텍스트로 변환되면 셀 구분이 무너지고 여러 값이 한 줄에 뭉쳐 나올
수 있다. 예를 들어 아래처럼 나타날 수 있다:

```
1차 실험 결과 **상까지의 거리 / 슬릿 폭 ** **0.1mm** **0.2mm** **100cm** 1 cm 0.35cm
**150cm** 1.4cm 0.5cm **200cm** 2cm 0.7cm -> 역산한 파장 값 계산식 : λ = ay/L
**조건** **0.1mm** **0.2mm** **100cm** 1000nm 700nm **150cm** 933nm 667nm ...
```

이걸 원문 그대로 raw_observations에 넣지 않는다. 행/열 구조를 문맥으로
재구성해서(별표 `**`는 표의 원래 굵은 헤더였다는 단서, 반복되는 조건 값들이
행/열 헤더라는 것을 인식) 의미가 통하는 문장으로 바꾼다. 이 경우:

> "슬릿 폭 0.1mm와 0.2mm, 스크린 거리 100~200cm 조건에서 무늬 간격을 측정하고
> 회절 공식으로 파장을 역산한 결과, 두 조건 모두 이론값(495~570nm)보다 크게
> 측정됨(0.1mm 조건 약 1000nm대, 0.2mm 조건 약 700nm대)"

수치는 보존하되(수치는 세특의 구체성을 높이는 요소이므로 삭제 대상이 아니다),
표의 형태 자체는 문장으로 풀어낸다. 표에서 뽑아낸 수치가 문맥과 안 맞아
보이면(예: 열과 행이 뒤바뀐 것 같으면) 확신 없이 넘기지 말고
`unresolved_conflicts`에 남긴다.

## 다중 보고서 모드

교사가 같은 학생의 같은 과목/항목에 대해 docx 여러 건을 한 세특으로 묶어달라고
요청하면 이 절차를 따른다. (한 건만 업로드됐다면 이 절은 건너뛰고 기존
절차대로 단일 활동으로 처리한다.)

### 순서 확정

이 순서는 보통 00(마스터 워크플로우)이 이 모듈을 호출하기 전에 이미
확정해서 넘겨준다(00의 "이름 기반 자동 탐지" 절차 참고 — 기본값은 업로드
순서이며, 제목·날짜·회차 같은 명확한 단서가 그와 다르면 단서를 우선해서
자동으로 정하고 한 줄로 통보한다. 순서 판단 자체가 불가능한 극히 드문
경우에만 교사에게 직접 확인받는다). 이 모듈이 순서를 스스로 정해야 하는
상황(00을 거치지 않고 이 절차만 단독으로 실행하는 경우 등)이라면 같은
원칙을 따른다.

- 순서가 이미 확정되어 입력으로 주어졌다면 그대로 따른다.
- 순서 없이 파일만 여러 개 주어졌다면, 업로드된 순서를 기본값으로
  삼는다. 제목·날짜·회차 표시 등 명확한 단서가 업로드 순서와 다르게
  나타나면 단서를 우선해서 순서를 정하고 추정 근거를 결과에 남긴다.
  업로드 순서조차 판단할 수 없는 경우에만(드묾) 각 파일의 제목을
  나열해서 교사에게 순서를 확인받는다. 순서는 최종 결과물에서 어느
  활동이 먼저 나오는지를 결정하므로 근거 없이 넘기지 않는다.

### 필드 일치 검증 (조용한 백그라운드 확인, 교사가 자기 과목만 쓴다는 전제와 상충하지 않음)

00은 같은 학생 이름으로 찾은 문서를 별도 사전 그룹핑 없이 그대로 이
모듈에 넘긴다 — 교사가 자기 담당 과목의 세특만 작성한다는 전제상 여러
문서가 서로 다른 과목일 가능성은 낮기 때문이다. 다만 이 모듈은 각 문서를
아래 "템플릿 인식"에 따라 개별적으로 처리하는 과정에서 자연스럽게
`field_type`과 (세특이면) `subject_label`을 판별하게 되므로, 그 값이
문서들 사이에서 일치하는지도 이 처리 과정 중에 함께 확인한다. 문제가
없는 절대다수의 경우 이 확인은 교사 눈에 보이지 않는다 — 값이 일치하면
그대로 조용히 다음 단계로 넘어간다.

- 하나라도 다르면(예: 한 건은 물리학Ⅱ, 한 건은 화학Ⅰ) 즉시 멈추고 교사에게
  알린다 — "두 보고서가 서로 다른 과목으로 보입니다. 이대로 하나의 세특에
  합쳐도 되는지, 아니면 각각 별도로 작성할지 확인해 주세요." 확인 없이
  임의로 합치거나 임의로 분리하지 않는다.
- 같은 과목이라도 학기가 다르게 보이는 등 애매한 경우도 `unresolved_conflicts`에
  남기고 교사 확인을 받은 뒤에만 진행한다.

### 개별 처리 후 결합

순서와 필드 일치가 확정되면, 각 문서를 지금까지의 "처리 절차"(개인정보
스크러빙 → 템플릿 인식 → 사실 단위 정리 → 인과관계 추출)에 따라 **완전히
독립적으로** 처리한다. 한 문서의 사실이 다른 문서의 raw_observations나
causal_chain에 섞여 들어가지 않는다 — 두 활동은 최종적으로 한 세특에
같이 실리지만, 사실 관계상으로는 끝까지 별개다.

각 문서의 처리 결과를 `activity_order`(교사가 확정한 순서, 1부터 시작)와
함께 배열로 묶어 출력한다. 자세한 스키마는 아래 "출력 스펙 — 다중 활동"
참고.

## 처리 절차

### 1단계: 개인정보 스크러빙 (가장 먼저, 예외 없이)

다음을 발견 즉시 제거한다. 2026학년도 기재요령 부속 AI 활용 가이드가 명시한
"AI 입력창에 넣지 않아야 할 개인 식별 정보" 범위를 따른다.

- **학생 이름, 학번**: 본문 어디에 있든(제목 옆, 표 헤더, "☺ 학번 : ☺ 이름 :"
  형태의 전용 행 등) 완전히 제거한다. 실제 사례처럼 이름·학번이 전용 표 행으로
  들어있는 경우, 그 행 전체를 통째로 버린다 — 일부만 지우고 나머지를 살리지 않는다.
  "30701(권미나) 외 0명"처럼 문서 상단 요약줄에 등장하는 경우도 동일하게 제거.
- 생년월일, 주소, 연락처 → 완전히 제거.
- 가족관계를 특정할 수 있는 표현(부모 이름 등) → 제거. 관계어만 있고 특정
  개인을 지칭하지 않는 서술("부모님과 상의하여")은 활동 사실의 일부이므로 남긴다.
- 파일명은 애초에 읽지 않는다(위 "입력" 항목 참고).

제거 사실 자체를 기록하지 않는다. 인물 지칭이 필요한 자리는 "학생은" 등
일반 명사로 자연스럽게 대체한다.

### 2단계: 템플릿 인식 및 field_type 결정

위 "템플릿 인식" 표를 참고해 field_type과 subject_label(해당하는 경우)을 정한다.

### 3단계: 사실 단위로 정리 (raw_observations)

템플릿의 각 섹션에서 검증 가능한 사실을 문장 단위로 뽑는다. 실험 결과·수치처럼
탐구 보고서 특유의 구체적 근거는 적극적으로 보존한다(이런 구체성이 나중에
03 평가 모듈의 "구체성" 기준에서 높은 점수를 받는 요소다). 같은 사실이 본론과
결론에서 반복 서술되어 있으면 하나로 합친다.

### 4단계: 인과관계 추출 (causal_chain)

템플릿 매핑 표를 따라 motivation/activity/competency를 채운다. 이 템플릿은
Q1이 동기를 명시적으로 담고 있으므로 **motivation을 null로 비워두지 않는 것이
원칙**이다(다른 형식의 문서, 예: 향후 추가될 창체 계열 템플릿에서는 동기가
암묵적일 수 있고, 그때는 기존 원칙대로 명시적으로 드러나지 않으면 null로 둔다).

## 출력 스펙

### 단일 활동 (문서 1건)

02(작성 모듈)의 입력 스펙과 정확히 맞춘다. `field_type`은 02에 별도 파라미터로
전달되고, 나머지가 `structured_activity_data`가 된다.

```json
{
  "field_type": "subject_setuk",
  "subject_label": "물리학II",
```

### 다중 활동 (문서 2건 이상, 순서 확정됨)

`field_type`·`subject_label`·`student_context`는 문서들 사이에서 이미 검증된
공통값이므로 최상위에 한 번만 둔다. 활동별 내용은 `activities` 배열에
`activity_order` 순서대로 담는다. 02는 이 배열을 받아 활동마다 독립된
문장 묶음을 쓰고, 절대 하나로 합치지 않는다.

```json
{
  "field_type": "subject_setuk",
  "subject_label": "물리학II",
  "student_context": "물리학II 교과 (개인 식별 정보 없음)",
  "activities": [
    {
      "activity_order": 1,
      "source_hint": "자기주도 탐구 보고서",
      "raw_observations": ["..."],
      "causal_chain": { "motivation": "...", "activity": "...", "competency": "..." }
    },
    {
      "activity_order": 2,
      "source_hint": "심화 실험 보고서",
      "raw_observations": ["..."],
      "causal_chain": { "motivation": null, "activity": "...", "competency": "..." }
    }
  ],
  "unresolved_conflicts": []
}
```

- `source_hint`는 교사가 어느 문장이 어느 보고서에서 나왔는지 나중에 확인할
  수 있도록 붙이는 짧은 식별용 라벨이다(보고서 제목 등). 개인정보는 넣지 않는다.
- 활동 사이에 사실을 공유하거나 인과관계를 새로 만들지 않는다 — 각
  `causal_chain`은 오직 그 활동 자신의 `raw_observations`만 근거로 한다.

`unresolved_conflicts`가 비어 있지 않으면, 00은 02를 호출하기 전에 이
목록을 교사에게 먼저 보여주고 확인받아야 한다. 문서에서 유효한 활동
기록을 찾지 못했다면(전부, 혹은 다중 모드에서 일부만) 그 사실을 그대로
알린다 — 다중 모드에서 일부 문서만 실패했다면 나머지로 계속할지 교사에게
확인받는다(임의로 제외하고 진행하지 않는다).

## 하지 말아야 할 것

- 개인 식별 정보(이름·학번·생년월일·연락처·가족 실명 등)를 어떤 형태로든
  이후 단계로 흘려보내지 않는다. 파일명도 예외가 아니다.
- 원문에 없는 동기·이유·평가를 추론해서 채워 넣지 않는다. 이 템플릿은
  동기가 명시적이므로 null을 쓸 일이 거의 없어야 한다 — 오히려 여기서
  motivation이 null로 나온다면 섹션을 놓쳤을 가능성을 의심할 것.
- 붕괴된 표를 원문 그대로(별표, 줄바꿈 뭉개진 상태로) raw_observations에 넣지 않는다.
- 아직 계획 단계인 내용("향후 추가 탐구 계획")을 이미 이룬 성취처럼 서술하지 않는다.
- 판별 안 되는 템플릿을 임의로 field_type에 끼워 맞추지 않는다.
- 다중 보고서 모드에서 field_type·subject_label이 서로 다른 문서를 교사
  확인 없이 임의로 하나로 합치지 않는다.
- 다중 보고서 모드에서 순서를 교사에게 확인받지 않고 업로드 순서나 파일명
  순서로 임의 추정하지 않는다.
- 다중 보고서 모드에서 한 문서의 사실을 다른 문서의 raw_observations나
  causal_chain에 섞지 않는다.
