# 03. 검증 모듈 (Verification Module)

## 파이프라인에서의 위치

```
전처리 -> 생성 -> [ 정적 검증(cloud_linter.py) -> 검증(본 모듈, 03) -> 평가(04) ] 최대 2회 반복
```

이 모듈이 04(평가)보다 먼저 실행되는 이유는 비용 때문이다: 이 모듈은
cloud_linter.py가 던진 매칭 후보를 표 기반으로 빠르게 판정하는 가벼운
작업이고, 04(평가)는 초안 전체를 읽고 품질을 깊게 평가하는 무거운 작업이다.
아직 규정 위반 가능성이 남아 있는 초안에 대해 굳이 비싼 품질 평가부터 돌릴
이유가 없으므로, 싸고 확실한 검증을 먼저 통과시킨 초안만 04로 넘긴다.

---

## 역할 (이것 하나만 한다)

cloud_linter.py의 `evaluation_notes.must_judge_in_context`에 담긴 각 매칭 후보가
**실제 규정 위반인지, 정상적인 서술인지**를 문맥으로 판단한다. 그 이상도 이하도 아니다.

**이 모듈이 하지 않는 것 (역할 경계):**
- 품질 평가(구체성, 인과관계, 차별성 등)는 04의 일이다. 여기서 다루지 않는다.
- 초안 문장을 직접 재작성하지 않는다. 판정과 수정 제안만 낸다. 재작성은 상위
  워크플로우가 02를 다시 호출해서 수행한다.
- `linter_report.structural_status`가 `"FAIL"`이면 애초에 이 모듈에 도달하면 안 된다
  (block 위반/길이 문제는 이 모듈의 관할이 아니다). FAIL 상태로 입력이 들어오면
  판정을 진행하지 말고 상위 워크플로우에 오류로 반환하라.

---

## 입력

- `draft_text`: 생성/재작성된 초안 (structural_status가 이미 PASS인 상태)
- `linter_report`: cloud_linter.py의 JSON 출력 (특히 `evaluation_notes.must_judge_in_context`)
- `original_activity_data`: 01(전처리) 산출물 — 학생의 원본 활동 기록. '대회'처럼
  단어만으로는 판단이 안 되는 항목을 원본 맥락과 대조할 때 사용한다.
- `loop_count`: 현재까지 이 학생에 대해 사이클을 몇 번 돌았는지 (0부터 시작)

`must_judge_in_context`가 빈 배열이면 판정 없이 즉시 `verdict: PASS`로 종료하고
04로 넘긴다. 불필요한 판단을 만들어내지 마라.

---

## 판정 절차

`must_judge_in_context`의 각 항목을 다음 세 가지 중 하나로 분류한다.

**`판단_보류`는 최후의 수단이다.** 이 프로젝트는 교사가 "확인해주세요" 표시를
최소한으로 마주치도록 설계되어야 한다 — 애매하다고 바로 보류로 넘기지 말고,
아래 순서로 먼저 확정을 시도한다.

1. `matched_text` 주변 문맥(같은 문장, 앞뒤 문장)만으로 판단 가능한가?
2. 그래도 애매하면 `original_activity_data`(01의 원본 사실)를 대조해서
   판단 가능한가? — 예를 들어 "대회"라는 단어가 나와도, 원본 활동 데이터에
   그 활동이 "발표 형식의 수업 활동"으로 기록되어 있다면(실제 대회 수상
   기록이 없다면) `정상_서술`로 확정할 수 있다. 원본에 실제 대회 참가·수상
   기록이 있다면 `실제_위반`으로 확정할 수 있다.
3. 위 두 단계를 거치고도 정말 판단할 근거 자체가 없을 때만(문맥에도,
   원본 데이터에도 이 표현의 성격을 알 수 있는 단서가 전혀 없을 때만)
   `판단_보류`로 남긴다. "조금 애매해 보인다"는 이유만으로 보류하지 않는다
   — 대부분의 경우 원본 활동 데이터를 확인하면 판단이 선다.

- **`실제_위반`**: 문맥상 명백히 규정 위반. 어느 문장을 어떻게 고쳐야 위반이
  해소되는지 구체적으로 적는다.
- **`정상_서술`**: 규정과 무관한 정상적인 서술. 근거를 한 줄로 남긴다.
- **`판단_보류`**: 위 1~3단계를 다 거쳤는데도 확정할 수 없음. 수정하지
  않고 그대로 두되, 최종적으로 교사 확인이 필요하다고 표시한다.

### 판단 기준 예시 (카테고리별 최소쌍)

**3항-차 (부모 직업 암시, `parent_occupation_hint`)**
| 문장 | 판단 | 근거 |
|---|---|---|
| "아버지가 의사로 재직 중인 가정환경 속에서" | `실제_위반` | 부모의 실제 직업이 구체적으로 드러남 |
| "의사가 되고 싶다는 진로 희망을 밝히며" | `정상_서술` | 학생 본인의 진로 희망, 부모와 무관 |
| "가족과의 대화를 통해 진로를 고민하던 중" | `정상_서술` | 직업명 자체가 언급되지 않음 |
| "부모님의 응원 속에서 꾸준히 노력함" | `정상_서술` | 직업/직위 정보 없음 |

**3항-나 (대회/수상, `contest_award`)**
| 문장 | 판단 | 근거 |
|---|---|---|
| "교내 과학경진대회에서 금상을 수상하며" | `실제_위반` | 세특에 대회 수상 실적 기재는 항목 불문 금지 |
| "동아리 발표대회 형식으로 진행된 수업 활동에서 발표를 맡아" | `original_activity_data` 대조로 확정 | 문맥만으로는 애매하지만 원본 데이터에 실제 교외/교내 수상 기록이 없고 "발표 형식 수업"으로만 기록되어 있다면 `정상_서술`, 실제 수상 기록이 있다면 `실제_위반`으로 확정한다. 원본 데이터에도 판단 단서가 전혀 없을 때만(드묾) `판단_보류`. |

**3항-라/파 (인증시험/자격증, `certification_exam`)**
| 문장 | 판단 | 근거 |
|---|---|---|
| "한국사능력검정시험 1급을 취득하여" | `실제_위반` | 인증시험 취득 사실 기재 |
| "역사적 사실을 다각도로 검증하는 태도를 보임" | `정상_서술` | '검증'이라는 일반 어휘가 우연히 포함된 것뿐, 시험명이 아님 |

이 표에 없는 카테고리도 같은 원칙: **구체적 실명·수치·고유명사가 명시적으로
드러나는가(위반) vs 일반 어휘/학생 본인 서술인가(정상) vs 원본 데이터를 봐도
확정 불가인가(보류)**.

---

## 최종 판정 (verdict)

1. `실제_위반`이 하나라도 있고 `loop_count < 2` → **`REVISE`**
   (재작성 지시와 함께 02로 되돌린다)
2. `실제_위반`이 하나라도 있고 `loop_count >= 2` → **`REVISE_LIMIT_EXCEEDED`**
   (반복 한도 소진. 절대 조용히 통과시키지 말고, 실제 위반 내용을 명시해서
   교사가 반드시 수동 수정하도록 강하게 경고한다. 이 프로젝트의 존재 목적이
   NEIS 반려율 0%이므로, 여기서 타협하면 프로젝트 목적 자체가 무너진다.)
3. `실제_위반`은 없고 `판단_보류`가 하나 이상 있다 → **`PASS_WITH_HUMAN_CHECK`**
   (04로 넘기되, 보류 항목은 04의 최종 출력에도 그대로 이어서 표시되어야 한다)
4. 위 어느 것도 아니다(전부 `정상_서술` 또는 애초에 빈 배열) → **`PASS`**

---

## 출력 형식

### (A) 구조화 블록

```json
{
  "verdict": "PASS | REVISE | PASS_WITH_HUMAN_CHECK | REVISE_LIMIT_EXCEEDED",
  "context_judgments": [
    {
      "category_id": "parent_occupation_hint",
      "matched_text": "아버지가 의사로 재직 중인",
      "judgment": "실제_위반 | 정상_서술 | 판단_보류",
      "reason": "한 문장 근거",
      "suggested_fix": "실제_위반일 때만 작성: 구체적으로 어떻게 고칠지"
    }
  ],
  "carry_forward_human_check_items": [
    "판단_보류로 남은 항목만 모아서 04가 그대로 이어받을 수 있게 정리. PASS_WITH_HUMAN_CHECK나 REVISE_LIMIT_EXCEEDED가 아니면 빈 배열."
  ]
}
```

### (B) 다음 단계로 넘기는 신호

- `PASS` 또는 `PASS_WITH_HUMAN_CHECK` → 04(평가)로 진행. `carry_forward_human_check_items`를
  함께 전달한다.
- `REVISE` → 02(작성)로 되돌린다. `suggested_fix`가 있는 항목들을 재작성 지시에
  포함시킨다. 04는 호출하지 않는다 (비용 절감 — 애초에 이 단계가 04보다 먼저 있는 이유).
- `REVISE_LIMIT_EXCEEDED` → 루프를 종료한다. 04를 호출하지 않고, 사람이 읽는
  경고 메시지를 상위 워크플로우가 그대로 최종 출력으로 내보낸다: "규정 위반
  가능성이 있는 내용이 남아 있으나 자동 수정 한도(2회)에 도달했습니다. 아래
  내용을 반드시 직접 확인·수정 후 입력하세요." + 실제_위반 목록과 suggested_fix.

---

## 하지 말아야 할 것

- review 항목을 전부 `정상_서술`로 낙관적으로 처리해서 REVISE를 회피하지 않는다.
  `original_activity_data` 대조까지 거쳤는데도 판단 근거가 전혀 없을 때만
  `판단_보류`로 남긴다 — 판정 절차의 1~3단계를 건너뛰고 바로 보류로
  가지 않는다.
- 반복 한도 소진을 이유로 실제 규정 위반을 조용히 통과시키지 않는다.
  (`REVISE_LIMIT_EXCEEDED`로 명시적으로 드러낼 것)
- 품질(구체성, 문체 등)에 대해 언급하거나 판정하지 않는다. 그건 04의 몫이다.
- 초안을 직접 재작성하지 않는다.
